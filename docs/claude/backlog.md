# Backlog

Forward-looking work list: missing features, fidelity gaps in shipped behavior, and design choices worth revisiting.
**Not a checklist** — completed work is removed, not ticked.

Ordering within each section leans toward predicted importance (popularity × ease, the Operating-goal weighting in [`../../CLAUDE.md`](../../CLAUDE.md)), but is **explicitly non-authoritative**: anything here is valid to pick up, and so is anything *not* here.

Most entries are triggers: the feature doc each points at holds the detail and the probe results, in its **Not modeled yet** or **Divergences** section.
An entry carries its detail here only when no single feature doc owns it.

## Completion process

When an item ships:

1. **Remove it from this file.**
   No checkmarks, no archive section — git records *what* changed; this file is only the open list.
2. **Ensure a `docs/claude/` deep-dive documents it** — explicit function/feature names, operational structure, probe-confirmed quirks and divergences.
3. **Ensure CLAUDE.md carries trigger keywords** linking to that deep-dive.
   The detail must be reachable from a fresh clone in one hop: CLAUDE.md keyword/phrase → deep-dive.
   Never rely on git history (or this file) for the *how*.

Per project convention, probe the live SQL Server 2025 reference instance before encoding "matches SQL Server" behavior.
**Re-verify an entry before building on it** — entries go stale as the surface moves, and this file has held claims that no longer reproduced.
The probing traps hit in practice are under [other differential oracles](sqllogictest.md#other-differential-oracles); the first is to re-run the oracle that found a bug rather than rebuild it from the entry's prose.

An entry marked **Deferred until requested** is parked by the user's call, not by cost: it stays listed so someone looking for it finds its findings, but isn't picked up autonomously — only when a user asks for that behavior.
Non-Latin collation work (the East Asian families, legacy and hidden collations, non-Latin code pages) is deferred this way as of 2026-09-29; the common Latin collations and code page 1252 stay active.
The same goes for work whose cost is mostly **data carried in the assembly** — a large dump of real's catalog, language or weight tables — as of 2026-10-16: it waits for a user or feature that needs it, while pure-logic work stays fair game however rarely it is used.

This file is the home for net-new non-function feature proposals too.
CLAUDE.md's **Not modeled yet** section is the complementary *descriptive* map (what raises `NotSupportedException` / Msg today, so the surface isn't over-promised); this list is the *prospective* one.
An item can appear in both with opposite intent.

### TDS network endpoint — follow-up phases

The endpoint ships with SQLBatch + RPC + Transaction Manager support and credential enforcement via the `CREATE LOGIN` registry (see [`tds-endpoint.md`](tds-endpoint.md)); EF Core runs over the wire through vanilla `UseSqlServer`.
Remaining phases, roughly in value order:

- **Tool shakedown** — point real client tools at the endpoint and harvest their exotic catalog queries / SET shapes into this backlog.
  Tool scope (user decision): tools a SQL Server + .NET developer already has — SSMS, sqlcmd, Visual Studio (SQL Server Object Explorer / DacFx), LINQPad; DBA-flavored tools like DBeaver are out of scope.
  **SSMS is the final boss** — an ongoing campaign, not a single leg: each surface is its own multi-round harvest, and clearing one unlocks the next.
  Cleared legs are recorded in the per-feature deep-dives (catalog surface in [`catalog-views.md`](catalog-views.md), wire behavior in [`tds-endpoint.md`](tds-endpoint.md)); the discovery harnesses are the gitignored `.vs/ssms-host` TDS host and the headless SMO property-bag drain.
  **Remaining frontier**: Table Designer, Activity Monitor, standard reports, and IntelliSense's background metadata harvest.
  Candidate follow-on legs within tool scope: Visual Studio's SQL Server Object Explorer (DacFx-driven, a different query dialect from SMO) and LINQPad.
- **What the SMO sweep leaves open** (the local-only `.vs/smo-sweep` drain; its standing result is under [other differential oracles](sqllogictest.md#other-differential-oracles)):
  - **`DBCC SHOW_STATISTICS … WITH STATS_STREAM`** (SMO `Statistic.Stream`) stays `NotSupportedException` — it wants the raw serialized statistics blob, which the simulator has no faithful source for.
  - **Settled — don't re-pitch: the shipped modules' own T-SQL isn't carried** — it is Microsoft's proprietary source, which no probe may read, so `sys.system_sql_modules.definition` stays NULL and SMO reads each system view / procedure / function as encrypted and won't script one or read its `Text`.
  - **Most system objects are unmodeled** — SMO lists some 1,400 procedures, 400 views and 140 functions the reference ships that the simulator doesn't.
    Nearly all of the procedures are replication, change feed, Fabric / Synapse, log shipping, agent, mail and policy plumbing; of the ones applications, drivers and DBA scripts call, what remains is `sp_MSdependencies`' whole-database listing ([`catalog-views.md`](catalog-views.md#the-ssms-era-sp_ms-helpers)).
  - **Storage accounting**: a LOB-eligible value always takes an off-row LOB page, where real keeps one that fits in row, every nonclustered index reports its heap's page count, and a partitioned table counts one page where real counts one per non-empty partition (`sp_statistics`' `PAGES`), so the sizes SMO reads run 10–90× the reference's.
  - **DacFx's import naming** — a bacpac import keeps `CREATE DATABASE`'s file names where DacFx names the primary pair `<db>_Primary.mdf` / `.ldf`, and index ids follow the loader's statement order rather than DacFx's.
- **A DML `OUTPUT` statement in a trigger body writes every row first** where real writes as it sends (see [`data-reader.md`](data-reader.md#a-dml-statements-output-rows)).
- **A DML statement writing as it sends reads ahead of real in a few shapes** ([`data-reader.md`](data-reader.md#divergences)): an `INSERT` source reading a view, function, derived table or subquery is read whole before its first write, a `MERGE` scanning its target or with a `NOT MATCHED BY SOURCE`, `DELETE` or capped action matches and computes every action first, and a derived or joined `MERGE` source in the target key's order is read whole — each where real streams; a seek's rows are chosen as the statement begins; and a `SERIALIZABLE` write takes its whole fence first.
  The `MERGE` scan and hash paths would judge each target row's action as the walk reaches it, which needs the walk to read on past its own writes as an `UPDATE`'s does (`TargetRowsAsTheyStand`); a derived source needs its order judged as a bare table's is (`BareTableMergeSource.ArrivesInKeyOrderOf`).
  Not chased, plan-dependent: the sorted inserts, hash-checked foreign keys and two-pass key updates real's plans choose by cost, recorded there.
- **Another request of the session waits for a statement producing its rows in the background** ([`data-reader.md`](data-reader.md#divergences)) — one under contention, waiting on a lock — where real runs the request beside it; a session's engine runs one request at a time here, so running beside it means the background production parking its request's state as a suspended statement does — from inside the lock manager's wait, where the production thread holds the request's executing thread, culture and lock-owner identity, and taking them back before it produces again — which touches the same-thread deadlock check and the abandoned-session sweep's reading of an idle session.
  The TDS endpoint's own worker pool (`EngineThreads`, [`tds-endpoint.md`](tds-endpoint.md#threading-model)) doesn't bring it closer: it decides which thread a request's continuation resumes on, while the production keeps a thread of its own and the session's one-request engine stays the obstacle — the park would have to be a point inside `LockManager`'s wait that hands the engine over and takes it back, for in-process and TDS requests alike.
- **A few `SERIALIZABLE` reads take their whole fence as they begin** — one through a nonclustered index in descending order, a descending or filtered index, a clustered key with a nullable or descending column, the union of an `OR`'s seeks — where real locks each key as it reaches it ([`locking.md`](locking.md#divergences-1)); `Selection.WalkKeyFence`, which every other seek reads through, would carry over once the seek cache's ordered view serves those orders.
- **A row-locking read keeps its lock on a row only a drawing, subquery-reaching or function-calling conjunct of its `WHERE` rejects** ([`locking.md`](locking.md#divergences-1)), where real lets it go; deciding by such a conjunct needs the residual `WHERE` to skip what the scan already asked, so it is asked once.
- **`PAGLOCK` residue** — a table loaded out of key order has the pages its splits left on real, where the layout here is a rebuild's, and an insert past a full last page locks only that page ([`locking.md`](locking.md#page-locks-paglock)); the position lock of a plain `READ COMMITTED` scan is settled — real's own isn't deterministic.
- **A bulk form in a trigger can't suspend its firing statement** ([`legacy-lob.md`](legacy-lob.md)), though the statement's own thread (`StatementCoroutine`) is the seam it would.
- **In process, a batch's messages don't count toward what a reader's batch runs ahead of** ([`data-reader.md`](data-reader.md#in-process-mars-overlapping-readers)), so a command beside a reader whose batch then prints runs after all of it, where over the wire it runs beside the procedure printing and is Msg 3980 behind an `INSERT … EXEC`'s body.

### Complex-query execution — perf residuals

The complexity batteries (`.vs/workload` `compare` subcommand + `complex*.sql`, local-only) are the standing measurement instrument; sub-4× ratios against the live reference are constant-factor or parallelism territory, larger ones name a missing execution strategy.
How to measure without fooling yourself is in [`plan-cache.md`](plan-cache.md#performance-impact); two strategies measured out and **settled — don't re-pitch** are recorded where they would have been built — a fan-out-aware semi-join crossover ([`subqueries.md`](subqueries.md#an-equi-correlated-body-switches-to-a-hash-semi--anti-join)) and building a join's hash over the smaller side ([`joins.md`](joins.md#equi-join-fast-path)).
Open residuals, in measured-impact order:

- **A statement that may reach a row-sending trigger still hands itself to a thread of its own** (`StatementCoroutine`, see [`data-reader.md`](data-reader.md#a-triggers-rows)), so beside one, a write whose own trigger only writes keeps paying the handoff, as one whose trigger may send does — 184–232 µs for EF Core 10's four-row `SaveChanges` at a load average of 5–8 (2026-10-17), against 106–152 µs once no trigger may send.
  The reach is read conservatively: any `EXEC` counts as sending, a trigger that writes counts as reaching every other trigger, and a write through a view always takes the thread; following a procedure's body, the nested and recursive trigger options and the base tables a view writes would narrow it.
- **A write through a view with an `INSTEAD OF` trigger reads every row of the view** — `UPDATE v SET … WHERE Id = @id` through a one-table view of 1,000 rows whose trigger joins `inserted` back to the base: 690 µs and 1.9 MB a statement (2026-10-17), `ReadViewRows` 57% of it and the trigger's joined `UPDATE` 19%, where the same update with no trigger seeks in ~7 µs; the parse is ~3%.
- **A write whose target is a common table expression scans the base table** — `WITH c AS (SELECT … WHERE Id = @id) UPDATE c SET …` over 1,000 rows: 240–275 µs and 540 KB a statement (2026-10-17), the per-row `WHERE` check of the body ~60% of it, where the equivalent write through a stored view with the filter outside seeks in ~7 µs; the body's `WHERE` never reaches the target walk's seek, and `WITH q AS (SELECT TOP (1) … ORDER BY Id) DELETE FROM q` (the queue shape) costs ~840 µs the same way.
- **A joined UPDATE whose partner filter leaves too many partners to seek hashes over the whole target** — `UPDATE o SET status = (o.status + 1) % 5 FROM ord o JOIN cust c ON c.cust_id = o.cust_id WHERE c.name LIKE N'cust1%'` (1,112 of 10,000 customers, 11k of 200k orders rewritten) measures 45–47 ms against real's 35 ms, and the same join filtered on `c.region = @r AND o.status = 1` and rolled back 20–35 ms against real's 10.6 ms (2026-10-17, medians of fifteen runs at a load average of 11–16; 77–85 and 43–55 ms before the write-target address map stopped hashing every scanned row and a stored column's decode stopped allocating its computed-column closure, see `RowAddressMap` and `Selection.DecodeOrCompute`).
  Profiled, what is left is the probe over all 200k target rows — the hash probe and its key's resolution about a quarter, the rewrite (`ComputeUpdatedRow`, `CommitUpdate`) about a fifth — and the scan's copy of each row it yields, 20 of the statement's 37 MB.
- **A residual WHERE runs its conjuncts in written order** — real answers `WHERE 10 / (k - 3) > -100 AND k <> 3` over a base table, testing the cheap conjunct first (probed 2026-10-17 against SQL Server 2025), and likewise applies a `HAVING` naming only grouping columns beneath the grouping (`GROUP BY k, 10 / (k - 3) HAVING k <> 3` answers there); a correlated `NOT EXISTS` written ahead of a selective equality runs for every tuple the equality would have rejected; reordering by cost would be legal (real guarantees no order) but moves which conjunct raises first, and a conjunct holding a subquery can raise from its body, so a reorder needs either a proof that neither conjunct can raise or the error-order story the pushdown sections tell before it is worth a measurement.
  The shape that motivated it, an equality on a materialized body's column, reaches that body ahead of the join through the [materialized-source narrowing](joins.md#the-where-narrows-a-materialized-source), which a later execution answers from a hash, so the `NOT EXISTS` already runs only on the tuples the equality kept there.
- **A buffered `SqlValue` result costs more live memory than the page image it replaced** — where a result is still produced whole (a MARS request over TDS, `ExecuteScalar`, a module body's `SELECT`; a statement-level result past the first window streams instead, see [`data-reader.md`](data-reader.md#rows-go-out-as-the-reader-reads-them)), the reader path carries the projection's own rows (see [`data-reader.md`](data-reader.md#the-row-form-the-reader-reads)), which cuts the statement's total allocation 35-43% but keeps a `SqlValue[]` per row alive while the reader is open: ~32 bytes per cell against the compact record, measured at 2.1× (4 columns) / 2.9× (10) / 3.4× (25) the buffered footprint on a 150k-row drain.
  The arrays are ones the projection allocated anyway — the encode was a *compaction* pass that then threw them away — so the trade is steady-state allocation against transient peak, and it is the right way round for the result sizes a test double sees.
  If a consumer draining a very wide, very long result feels it, the mitigation is a **form gate in `SimulatedSqlResultSet.MaterializeRows`**: encode when the projection is wide enough that compaction pays, keep values otherwise (the two forms are answer-for-answer identical, so the choice is pure policy). Wall-clock measurements on the dev box were too noisy to place the crossover — that measurement is the first half of the work.
- **A text the compile memos don't serve is parsed twice**, once by the batch-compile walk and once to run.
  Measured 2026-10-08 with a throwaway build that skipped the walk (ADO.NET, one case per process, median of 0.25 s blocks after a 2 s warm-up), the walk is 41% of an ad hoc point `SELECT` (21.6 → 12.7 µs), 37% of an ad hoc join and aggregate (52.8 → 33.3 µs), 32% of an ad hoc single-row `UPDATE` (13.0 → 8.8 µs) and 46% of a repeated batch that creates, fills, reads and drops a `#temp` (84.9 → 45.6 µs); a repeated parameterized batch or procedure call pays none, `compiledBatches` and `ModulePlan` skipping it, and a repeated `sp_executesql` now pays none either (its compile is remembered, 21.2 → 15.2 µs).
  Where execution outweighs the parse the share shrinks: replaying sqllogictest's `index/in/1000` single-threaded (measured 2026-09-27), the walk was 8.8% of process CPU, and skipping it bounded the win at 13.0 → 12.1 s.
  A CPU profile of one-off texts (2026-10-08, see [`plan-cache.md`](plan-cache.md#one-off-texts-a-cpu-profile-of-the-parse)) took the parse's constant factors — keyword classification, column-name matching, object-name hashing and the walks' allocation — and one-off statements 27–52% with them, leaving the walk 35% of a one-off point `SELECT` and the two parses 63%.
  A second pass (2026-10-08, see [`plan-cache.md`](plan-cache.md#one-off-texts-the-profiles-leftovers)) took the leftovers it named — a parse-time column-resolution memo, state-passing walks, a frozen arity lookup, the compile context skipped for a remembered compile — and one-off statements another 0–35% (the point `SELECT` 15%, SMO's column query 35%).
  What is left of them: nullability, volatile and identity columns and the wire flags are read off a statement's plan by set operations and `CREATE VIEW`, so skipping them in the walk needs the walk to know a statement's query is its last word; the second `BatchContext` of a first compile (~1.9 KB, mostly fields the walk reads); and each name's first resolution and the read recorder's own column scan.
  Reusing the walk's `Selection` for the run isn't sound as-is: the walk parses under `CreateTimeBinding` in skip mode, which takes `DataLockPlan.Bypass` and no data locks, evaluates no FROM-less row, binds a missing table to a placeholder, skips the `TOP (@p)` declared-type check and settles inlining and optimizer refusals the run doesn't.
  Skipping the walk for a one-statement batch isn't a shortcut either: a compile error surfaces at `ExecuteReader` where a run-time one can surface at `Read()`, the batch-abort rules differ, and the walk alone sends what a compile sends (the inlining Msg 208, a join-order warning) and settles Msg 8622.
  The prerequisite for any real win is moving those parse-time run-only effects into an execution step, so that a skip-mode plan equals the run's; short of that, the levers are the parse's own constant factors, which every unique text pays twice.
- **A scalar function call still builds and dispatches a child batch** — `RETURN @x * 2` called per row costs ~1.3 µs a row and a `DECLARE` / `IF` / `SET` / `RETURN` body ~3.0 µs at a load average of about 16 (measured 2026-10-17, once the body's values and conditions came to be kept across calls — see [`programmable.md`](programmable.md#body-batches-and-the-per-statement-freeze)).
  What is left is mostly the child batch itself: its `BatchContext` (~1.1 KB of fields), `ParserContext` (~0.55 KB) and `StatementContext` (~0.35 KB), the dispatch loop's per-statement iterators (~0.45 KB) and each statement's lifecycle, and the parse of a `DECLARE`'s type; none has a cheap reset, which is what pooling a batch per function would need, and real inlines such a body into the calling query.
- **A multi-statement function's writes to its return table parse per call** — the table is a new `HeapTable` each call (its rows escape the body to the caller's enumeration), and a plan binds the table it writes, so the `INSERT @r …` statements decline as any table-variable target does; a loop calling a two-`INSERT` function costs ~17.7 µs a call (measured 2026-10-08), of which the return table's first page (8 KB) and heap are a share no plan removes.
  Keeping the table across calls as the trigger pseudo-tables are kept would need the caller's enumeration to finish with one call's rows before the next call refills them, which a correlated `APPLY` over the function doesn't promise.
- **Intra-query parallelism is the systematic remainder** — the scan-bound shapes that survive every constant-factor pass (`daterange.*`, `conditional.agg_pivot`, `window.three_sorts`, `union.dedup_big`, the year-aggregating reports) sit at 1.5-3.5× live with real running DOP 8, and profiling shows the simulator using *less CPU* than real on several of them — the gap is parallel execution, not waste.
  An unprofiled small neighbor: a `TOP (1000)` ordered by the PK over a wide table sits ~3× (`format.heavy_1000`).
  **Covered so far**: the streaming single-grouping-set aggregate path's per-row *consumer* work forks across worker threads while the calling thread produces the stream — built, tested and measured at 1.2-2.4× on a single-session battery, and **off by default** because the concurrent workload driver loses 25-30% throughput from even a handful of forks (see [`query.md`](query.md#parallel-grouped-accumulation-built-proven-off-by-default) for the gates, the merge contract and the error rule).
  **What that leaves.** Three things, in the order they are worth doing:
  1. **The residual process-wide cost of forking at all** — the AdventureWorks driver loses its throughput across a phase in which the fan-out never engages again, so the cost outlives the forked statements. Thread lifetime (a retiring pool; a 1 ms idle timeout) and block-allocation size were both ruled out by measurement. Until this is explained the default cannot flip, and explaining it is the whole gate on the rest of the work.
  2. **The producer is still serial**, so Amdahl bounds every join-fed aggregate: a bare `COUNT(*)` over the 228k-row `Invoices ⋈ InvoiceLines` join costs ~70 ms on its own. Parallelising the join itself means building the hash once and partitioning the probe side, which is a change to the join driver rather than to the aggregate path.
  3. **The shapes the pilot doesn't reach**: an ordinary (non-aggregate) projection, `DISTINCT` and the set-operation dedup, the window executor's sorts, and a high-cardinality `GROUP BY` (the per-worker maps' merge is what makes 73k groups lose). Each needs its own merge argument; none inherits the aggregate path's.
  **Scheduling (user direction, 2026-08-05): none of the above proceeds until the easier algorithmic wins elsewhere in this section are exhausted** — every "parallelism territory" shape profiled so far hid an algorithmic or constant-factor win under the label, and the MAXDOP-1 comparison confirms most residual ratios are constant factors at equal threading.
  Item 1's unexplained fork cost is additionally the hard gate on flipping the pilot's default, whenever the topic reopens.
- **What EF Core's functional classes still spend in the simulator** (measured 2026-10-03, see [`plan-cache.md`](plan-cache.md#second-pass-the-simulator-inside-the-test-process)) — inside a test process the simulator's methods mostly never leave tier 0, which is the consumer's tiering settings rather than the library's; of what the library controls, the costs left are:
  an uncached statement whose batch hasn't compiled before builds two `BatchContext`s, each with eager dictionaries, so `SELECT 1` costs ~3 µs and ~9 KB;
  the first catalog read builds every catalog view (~50 ms per process, about half of it compiling the `Register*` methods), and `BuiltInResources`' initializer still carries `sys.types`' rows, the configuration table and the time-zone list (~7 ms of that);
  a correlated subquery reading only an outer-outer row re-runs per inner row — Northwind's `EXISTS` over three `TOP (1)` scalar subqueries on the customer runs them 20,000 times for 8 customers (~27 ms), where a memo keyed by the consulted outer values would run them 24 times;
  and a leftmost uncorrelated derived table inside a per-row body (`EXISTS (SELECT 1 FROM (SELECT TOP (100) … ORDER BY …) o1 WHERE …)`) re-sorts per outer row until the semi-join switch (~40 ms), because its consumer may stop early and the statement-scoped reuse the non-leftmost slots take only stores a fully drained source.
  The first pass's per-row ordered seek (`CappedCandidates`) didn't rank in these six classes.

## Over-permissive register

The simulator accepting what real rejects is the more dangerous divergence direction — the query passes here and fails in production — and it is invisible to any sim-only failure list (see the reverse delta under [other differential oracles](sqllogictest.md#other-differential-oracles)).
This is the standing list: each entry names the error real raises that the simulator doesn't, and the linked deep-dive carries the detail.
Entries are verified against the simulator, so one that no longer reproduces is removed rather than re-worded.

- **`FORCESEEK` and index-hint residue** — a `LIKE` on a column a hash or merge join equates with a `FORCESEEK` table's is taken as implying the inner seek, an `INDEX` hint naming a spatial index runs beside a predicate it can't answer, and under `QUOTED_IDENTIFIER OFF` a seek on a computed column's index is taken, each where real raises **Msg 8622** → [`query-hints.md`](query-hints.md#not-enforced).

The opposite direction — the simulator refusing what real accepts — includes CLR registration: a `SAFE` assembly referencing the APIs the simulator's own verification denies (Msg 6218 / 6211), which real registers, an assembly real would trust for its signature, and a reference to another assembly registered in the database (Msg 6503 here) → [`clr-assemblies.md`](clr-assemblies.md#not-modeled-yet).
It also includes the deterministic nesting caps, which sit below real's stack-dependent thresholds (paren 500 and subquery 83 against real's 1015 / 168, deep function nesting surfacing Msg 8631 rather than Msg 191 on tight threads) to keep Msg 191 firing with headroom before the stack probe; closing that wants a slimmer function-argument recursion frame → [`grammar.md`](grammar.md#expression-depth-limits-msg-8631--msg-191--msg-125).

## Live-but-untested surfaces

Reachable code paths no test exercises, from a coverage run (`dotnet test --collect:"XPlat Code Coverage"` → reportgenerator) — not gaps in behavior, gaps in the safety net.
The uncovered `DebugDisplay` / `ToString` debugger helpers and `Stream` boilerplate overrides are deliberately not worth testing; what remains is this list.

- **`LikeMatcher.Cache`'s collation key component can't be varied by any test** — the resolved collation is a per-expression-node constant in every shape reachable through SQL, so mutation-testing it catches nothing; it guards a hypothetical future caller that rebinds a node's collation between executions.

Worth re-measuring after a large bundle rather than routinely, and worth acting on when it does run: a pass that probes each path it tests against real finds bugs there — `sp_cursorprepare`, untested, read its parameters one position late.
It found two pieces of dead code, and every gap that was then covered turned out to be hiding a behavior bug — uncovered code here has consistently meant *wrong* code, not just unwatched code.

## Design choices to revisit

Queued structural refactors (behavior-neutral, one per commit, each proven by the full gate plus a timing A/B):

- **`Selection`'s long phases** (`ParseSingleFromSourceCore`, `ParseQueryBlock`, `BuildSqlProjection`, the aggregate builder) split opportunistically, when feature work next touches them — they sit on measured hot paths, so each extraction takes a perf A/B.

Settled design choices:

- **`APPROX_COUNT_DISTINCT` counts exactly — settled, don't re-pitch.**
  Real's answer is a 4096-register HyperLogLog estimate, but its hash isn't identifiable from query outputs and its answer varies between batch- and row-mode execution of one input, so real itself guarantees no particular estimate and exact is the one answer within its error everywhere → [`query.md`](query.md#the-approximate-aggregates).
